> 结果见[审计执行记录](../qa/code-reuse-audit.md#升级执行记录2026-10-09)及[浏览器矩阵](../qa/browser-matrix.md)。
> 2026-10-08 复核修订：补齐列表覆盖与可选补全、响应分支、授权边界差异、采集异常优先级、跨组件样式及回退限制。
>
> 依据：[项目复用审计](../qa/code-reuse-audit.md)。适用范围：五个 OJ Adapter、领域与应用规则、网络与权限模块、两个页面及测试基础设施。
>
> 本轮目标是减少独立维护的重复规则，让现有行为可验证、模块职责明确、新增来源有固定接入步骤。保留现有技术栈与数据协议，按小批次迁移。

## 1. 升级目标与范围

本轮优先实现以下结果：

| 目标         | 完成后应能观察到的变化                                                       |
| ------------ | ---------------------------------------------------------------------------- |
| 可靠         | 采集完整性、身份变化、取消、限流与 Cookie 收尾有明确合同；每次迁移有回归证据 |
| 可维护       | 名称、固定站点、消息公共字段与公共采集规则各有唯一维护入口                   |
| 可扩展       | 新增 OJ 使用现有端口及小型策略，UI 不需要新增来源分支或导入采集实现          |
| 实际减少重复 | 洛谷/QOJ 复用采集状态与规则，错误样板、测试环境和下拉基础样式不再分别维护    |

不以文件数量、某个文件缩到多少行、删掉多少测试作为成功标准。记录净代码变化与维护点变化，但不预设缩减百分比。

范围约束：

- 不更换 React/WXT/TypeScript，不引入大型 schema、RPC、任务调度或插件框架。
- 不扩大同步范围、分页预算、网络权限或认证能力；不做全历史采集或云端同步。
- 不改变存储与消息 schema 2，不重写账号身份键、提交唯一键、偏好结构或单写入者模型。
- 各站原始 verdict、语言、HTML/JSON 结构、认证回退、下一页依据和游标规则继续留在站点模块。
- 长文件按职责拆分是后续维护手段，不作为本轮主要去重成果。

## 2. 兼容合同：先固定行为，再迁移实现

以实施起点的代码、回归测试和当前 README 为行为基线。S0 记录 commit、相关未提交差异及检查时间；之后其他任务修改同一模块时，针对该模块重新确认基线，不混入或回退其他任务的修改。审计中的 503 个通过用例是历史快照；开始实施时重新记录基线，不硬编码测试数量。

必须保持：

1. 添加账号只验证身份与保存配置，不自动采集记录。重新授权保留已有 enabled 选择和缓存，递增凭证版本。
2. 采集使用冻结的毫秒闭区间 `[since, until]`，默认最近 7 天，最多最近 35 天。显示筛选范围与采集范围仍是不同用途。
3. 窗口外记录不进入本轮结果、不占记录额度、不请求单条详情；此前已缓存的范围外记录继续按保留策略管理。
4. 列表首个成功页之前的失败仍是失败；已取得可靠页面后，允许的后续错误可以产生 partial。常规身份错误继续抛出，用户取消丢弃本轮结果；deadline 与其他错误同时出现时，按 4.4 的现有优先级迁移，不擅自重排。
5. complete 必须有尾部、可靠时间边界或所有流完成的证据；尚未完成的列表因额度、重复页、未知分页、无效记录或 deadline 停止时不能伪报完整。列表已完整而可选题名、详情或品牌补全失败，只增加相应诊断，不能一概把列表 coverage 降为 partial。
6. 只有完整采集更新 lastSuccessAt；partial 可以合并已验证记录，保留旧成功时间；用户取消丢弃本轮新结果。
7. 账号任务的共享键、凭证版本、代际失效、一个运行任务与一个待执行窗口、15 分钟任务时限保持不变。清空/删除后旧采集结果不能回填；不同清除命令对待授权操作的影响按下表保留。
8. 每轮同步冻结分页配置；同 origin 共享逻辑页队列与冷却。保留 1.5–600 秒基础间隔、0.1 秒步长、至少 1 秒实际延迟及既有浮动上限。保存/恢复默认只影响下一轮，Hydro 实例继续共享来源设置但按不同 origin 排队。force 只绕过 freshness，不绕过节流、预算或 429 冷却。
9. Cookie 恢复完成之后才能释放对应锁；Hydro 会话锁、分页锁与 Cookie 锁保留独立实例和既定嵌套顺序。
10. 数据写入仍只经后台 StoragePort；网络请求在事务外；公共响应不能包含凭证或内部活动缓存。
11. Hydro 实例和 domainId 精确隔离；公开数据 origin、导航 origin 与凭证 origin 分别校验。
12. 保留原有记录选择顺序、重复记录取值、诊断语义、错误字段和进度统计方式。抽取代码本身不顺带改变政策；保留“覆盖完整且有补全警告”的组合。

以下易混淆状态需要分别对照，不能在共享 helper 中合并：

| 状态或操作             | 当前语义与迁移限制                                                                                                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 列表 deadline          | 没有成功列表页时失败；已有成功页时由来源决定 partial；不得伪报列表完整                                                                                                                   |
| 可选补全 deadline/失败 | 例如 AtCoder 列表已完整后，题名或详情到期仍保留原 coverage，并附 enrichment-incomplete；品牌刷新有自己的警告。现有提交判断可能继续更新成功时间，不能按 signal.aborted 或警告数量统一降级 |
| syncAccountIds 未配置  | 默认选择启用账号；不是“选择空集合”                                                                                                                                                       |
| syncAccountIds = []    | 用户明确选择不采集任何账号；不得用 truthy/falsy、数组长度或默认值运算恢复全部账号                                                                                                        |
| DELETE_ACCOUNT         | 取消该账号采集；删除其账号、凭证、提交、syncState 与选择项；保留可能共享的品牌和活动缓存，不取消所有待授权操作                                                                           |
| CLEAR_SUBMISSIONS      | 取消当前采集，只清空 submissions；保留账号、凭证、syncStates、缓存与偏好，也不等同于取消待授权操作                                                                                       |
| CLEAR_ACCOUNTS         | 使待授权操作失效并取消采集；清空账号、凭证、提交、syncStates、品牌/活动缓存；保留其他偏好，将 syncAccountIds 设为 []                                                                     |
| CLEAR_DATA             | 使待授权操作失效并取消采集，经 storage.clear 重置整份数据和默认偏好；不沿用 CLEAR_ACCOUNTS 的偏好保留逻辑                                                                                |

清除操作具体行为以 `background.ts`、AccountService 和 StoragePort 为准；响应 helper 只封装回复，不能顺带统一这些业务转换。当前 revision 不是跨清空单调增长的 CAS，不能用它单独判定页面回包一定更新或更旧。

历史账号/分页计划中仍有“授权后首次采集”的描述，与当前实现及 README 不一致。阶段 S0 已将这类条款更新到当前合同；本轮不恢复该流程。其他已实施合同继续参考[分页与覆盖计划](./submission-sync-window-and-pagination-throttle.md)和[账号系统 Spec](./account-system-refactor-spec.md)。

发现现有缺陷时，先用针对性用例记录，单独提交修复及行为说明。复用迁移与行为修正分别评审，避免无法判断差异来自哪里。

## 3. 目标模块结构与依赖约束

保持现有分层，补齐轻量来源定义和真正共有的小策略。以下新路径是建议落点；实施时允许合并过小模块，但责任与依赖方向必须保留。

| 模块                         | 责任                                                 | 禁止承担的责任                                           |
| ---------------------------- | ---------------------------------------------------- | -------------------------------------------------------- |
| `src/domain/`                | 端口、数据类型、身份/窗口/覆盖/授权输入等纯规则      | 浏览器 API、站点请求、HTML 解析、来源实现注册            |
| `src/sources/definitions.ts` | 只读来源描述与固定站点事实，依赖领域类型             | 网络、浏览器、Adapter 实现、账号凭证值                   |
| `src/adapters/<source>/`     | 站点身份、请求组织、解析、归一化、分页证据与特殊政策 | 写主存储、自己的冷却队列、UI 状态                        |
| `src/adapters/shared/`       | 已归一化页面状态、采集失败分类、HTML 基础处理        | 根据 SourceId 切换 raw-record 算法、浏览器 API、网络重试 |
| `src/application/`           | 授权/同步用例、生命周期、提交事务、公共 DTO          | 解释 HTML、站点页码或活动内部字段                        |
| `src/platform/`              | HTTP、Cookie、权限、队列和可取消等待                 | 采集覆盖判断、结果合并、页面文案                         |
| `entrypoints/shared/`        | UI 消息客户端、共享组件、展示配置与基础样式          | 导入完整采集注册表、直接写主存储                         |
| `tests/helpers/`             | 内存端口、异步控制、基础响应与合法测试对象           | 使用被测算法生成预期值、替用例隐藏触发顺序               |

```mermaid
flowchart TD
  UI[页面与共享 UI] --> MSG[消息合同与客户端]
  UI --> DEF[轻量来源定义]
  UI --> PERM[纯权限计划与用户手势申请]
  BG[后台装配入口] --> APP[应用用例与存储事务]
  BG --> NET[网络与浏览器实现]
  APP --> REG[Adapter 实现注册表]
  REG --> AD[站点 Adapter 与共享采集策略]
  AD --> PORT[领域端口与纯规则]
  APP --> PORT
  NET --> PORT
  NET --> DEF
  PERM --> DEF
  DEF --> PORT
```

箭头表示依赖。应用层继续可以选择 Adapter；页面只读取描述。平台为领域端口提供实现，后台负责组装单例并注入，Adapter 不自行创建另一份 HTTP、分页或冷却实例。

在 S1-B 完成时增加窄范围静态依赖门禁：domain/sources 的运行时依赖链不得引入 application、adapters、entrypoints、平台实现或浏览器 API；页面及其依赖链不得到达完整 Adapter 注册表或五个来源的采集实现入口。只检查 `adapters/index.ts` 的直接导入不足以防止绕过。

检查应能解析静态 import、re-export 与字面量动态 import，识别路径别名，忽略真正被擦除的 type-only 导入；无法解析的项目内运行时依赖或非字面量动态导入明确报错，不默认为安全。使用已有解析工具，补少量正反依赖 fixture；脚本纳入 package.json 的独立检查命令，并在 S1-B 起每单元及最终门禁执行。不写泛用架构分析框架，也不把依赖检查写成只对当前文件名有效的字符串搜索。

页面目前使用的 Hydro 地址规范化、语言展示 helper 可以保留为明确的小叶子模块；若其依赖引入站点采集实现，再单独拆到纯模块。依赖限制不等于禁止所有包含 `adapters/` 的路径。

## 4. 关键设计

### 4.1 来源定义与实现注册：R02

保留 `SOURCE_IDS` 作为来源集合和顺序的权威定义。新增 `sourceDefinitions`，以 `satisfies Record<SourceId, SourceDefinition>` 保证穷尽覆盖。定义包含当前 metadata、默认官方首页和固定网站 origin；Hydro 的实际 origin 仍来自账号配置。

约束与迁移方式：

- 先搬迁当前描述，不更改名称、来源排序、availability、授权模式、默认模式、凭证字段、dataOrigins 或字段必填语义。
- 元数据接口逐步改为只读数组与只读字段；定义以不可变值使用，不允许消费者根据某账号改写共享描述。
- Adapter 的 metadata 引用同一份描述，不在站点实现内复制对象；前端、权限模块和网络固定 origin 表改读定义。
- 实现注册表改为穷尽的 `Record<SourceId, OJAdapter>`，保留现有查询接口作为迁移适配；校验 registry key 与 metadata.id 一致。`satisfies Record` 本身不能证明这两个值相等，需关联类型或注册初始化校验。保留 Adapter 对象引用和后台实例，不因转换为 Record 复制实现或重新创建采集器。全部消费者迁移后删除临时适配。
- 默认分页政策仍由已有 `domain/pagination-policy.ts` 维护；不另在来源定义重复登记数值。图标路径留在 UI 配置，名称读取来源描述。
- manifest 权限仍显式声明；固定 origin 可复用，是否默认授予/可选申请仍由构建配置决定，并由 manifest 审计验证。不得自动把所有来源或 dataOrigins 改成默认 host_permissions。

权限模块从相同 origin 事实派生 Chrome permission pattern；HTTP 与 Cookie 模块分别执行各自政策。公开数据端点不自动成为导航或 Cookie 目标。Hydro 不能登记为仅允许官方站点的 fixedOrigin；保留 `createHydroOJInstance` 的默认官方 origin、地址规范化及显式域规则，官方首页描述不替代用户选择的实例范围。source 枚举顺序、Adapter 列表及 UI 选项均按既有顺序构造，不从对象插入顺序猜测。

来源的静态 displayName 与账号/实例的 label、providerDisplayName、branding.name 是不同数据。元数据去重只删除静态映射，不统一各页面既有的实例名称回退顺序；例如 Timeline 使用账号 label，诊断可能优先显示缓存品牌名。实例配置、账号展示名和品牌刷新状态不能被全局来源定义覆盖。

sourceId、面向用户的 displayName 与传输层的稳定诊断名称也不能互换；不要因为读取同一来源定义就改写既有 Error.message 或诊断标识。值或语义不同的名称应注明用途，不能当作完全相同的重复项删除。

完成标准：新增一个 SourceId 后，缺少描述、实现、分页默认值或 UI 图标时应由类型/构建检查暴露；页面不再维护独立的 source 名称与固定首页映射，也不再导入实现注册表。

### 4.2 消息客户端与响应构造：R03

在 `entrypoints/shared/runtime-client.ts` 提供统一发送入口；在现有 application/messaging 层补充 envelope 与响应构造 helper。第一版发送入口接受已经完整构造的 RuntimeMessage，返回 RuntimeResponse 联合类型，由调用方检查 `ok/type`；不开放让调用者指定任意返回类型的泛型。公共字段用独立的类型严格构造函数创建，不能让 send 用 `object` 接收输入、猜 type 或覆盖已有 requestId。

具体要求：

- 公共 schema 字段来自 `MESSAGE_SCHEMA_VERSION`；requestId 创建集中，但必须允许显式传入同步运行的 requestId，保留进度通知关联。
- 浏览器返回值先作为 unknown；集中检查版本、requestId、ok、响应分支以及该分支必要载荷结构。复用已有领域谓词，避免一个 `as Extract<...>` 冒充验证。
- 异常响应与传输拒绝有稳定的失败分类，调用方转换为现有页面反馈；未检查响应 type 前不能访问 data/result/account。
- 后台 `STATE/UPDATED/AUTHORIZED/SYNC_RESULT` 构造继续通过 `publicStoredData` 脱敏；共用公共字段，保留不同分支的真实载荷。
- RuntimeMessage 的后台严格校验、sender 检查、同步通知顺序检查继续存在。请求客户端不自动重试授权、删除、清空或其他变更命令。
- 响应 envelope 检查不等于修复损坏缓存；存储对象的完整结构校验属于存储边界。若需要补充领域谓词，在单独模块共享谓词，消息拒绝与存储修复策略分开。

成功命令与响应对应关系固定如下；所有命令都可能返回没有 type 字段的 `ok: false` 错误分支，该分支只要求合法的公共字段及 error.code/message，不能误判为非法响应：

| 命令                                                                                                                 | 成功响应与必需载荷                                                       |
| -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| GET_STATE                                                                                                            | STATE / data                                                             |
| SYNC_REQUEST                                                                                                         | SYNC_RESULT / result.data、sources、progress、addedRecords               |
| UPDATE_SYNC_ACCOUNTS、UPDATE_SYNC_RANGE、UPDATE_PAGINATION_POLICY、DELETE_ACCOUNT、CLEAR_ACCOUNTS、CLEAR_SUBMISSIONS | UPDATED / data                                                           |
| CLEAR_DATA                                                                                                           | CLEARED，不要求 data                                                     |
| AUTHORIZE_ACCOUNT                                                                                                    | AUTHORIZED / data、account、superseded；superseded=true 仍是合法成功分支 |
| DETECT_BROWSER_SESSION                                                                                               | BROWSER_SESSION / source、account；未登录或 unsupported 仍是合法检测结果 |

先校验 `ok` 再区分分支；required/optional 字段按现有 DTO 定义，不能要求可选 coverage、paginationBySource 或会话用户名始终存在。公共 data 检查复用领域结构规则，不能调用存储迁移将坏响应变成默认空数据，也不能因 guard 不完备而宣称已完成深层数据验证。对旧的合法快照、缺失可选配置和部分/覆盖未知结果做兼容用例；有损坏缓存时单列存储修复，不直接清空全部账号或记录。

测试 mock 必须回显实际请求的 requestId；不能为兼容固定 `state/test` ID 的旧 mock 而放松生产关联检查。公共客户端不增加全局消息监听、短超时、自动取消或并发合并；页面关闭/消息通道中断不代表后台同步已取消，不能超时后自动重发仍在执行的命令。

保留已有 UI 竞态控制：设置 GET_STATE 的 loadSequence 与卸载清理；PaginationSettings 保存后 await 权威状态刷新再重置草稿；Timeline 的选择/范围保存队列及失败恢复；授权检测的 revision 与提交互斥。不要用统一客户端替代这些状态职责，也不要仅按 revision 大小决定是否覆盖状态。同步仍先注册本轮进度监听再发送请求，以事务后的 SYNC_RESULT 为权威终态，晚到通知不能覆盖最终结果。

先迁移设置读取与 PaginationSettings，再迁移授权与 Timeline。GET_STATE 的不同响应、错误版本、缺失载荷、requestId 不匹配和传输失败均应变成可见失败，不再依赖泛型断言继续渲染。

### 4.3 错误与授权纯规则：R04、R07

扩展现有 `domain/errors.ts` 的构造能力，优先复用 source/requestId 上下文。kind、stage、messageKey、retryable、userAction 的政策由明确参数或已验证的默认规则决定；保留 `AdapterFailure.fromTransport`，避免重复包装已分类错误。

cause 与原始拒绝值只保留在内部错误链中，不能随公共响应透出或直接 stringify 进日志。公共诊断只用既有的稳定 code/stage/messageKey/requestId 与不含值的 Cookie 范围信息；复用构造器不能新增 headers/body/credentials 的调试输出。

迁移前为各入口登记现有错误字段。例如 QOJ 对普通 HTTP 400 的 retryable 与洛谷/AtCoder 不同，第一轮必须显式保留这一差异。统一政策若有必要，在后续独立修正中完成。

新增纯授权规则模块 `domain/auth-input.ts`，共享字段声明、基础谓词与 issue/messageKey，但保留明确的“表单准备”与“服务命令校验”入口。二者不是相同的规范化函数，不能为了共用一个返回对象抹掉现有输入边界；站点仍确认真实身份。

- identifier 在表单与服务均裁剪；表单裁剪非密码字段，服务当前验证它们是否为空白后保留收到的原值。不能把表单的 trim 无条件施加到服务直接收到的命令上。
- 密码原值保持不变。当前表单的必填密码判断为空字符串，服务为 `!value?.trim()`；纯空格密码可能在不同阶段被拒绝。第一轮分别保留判断位置、反馈和权限请求时序，统一空白规则属于单独行为修正。
- 表单只构造已声明字段；服务拒绝未知凭证字段，且此检查发生在 public-handle/browser-session 丢弃保存用凭证之前。不能先静默过滤未知字段再验证。可选字段的空白/省略、空字符串与 undefined 按各入口现有语义保留。
- Cookie 解析仍调用既有领域及站点 helper；credentialValue 会 trim，不能将其用于要求保留原值的密码处理。
- 凭证条目的基础合法性谓词可同时用于消息与存储；消息拒绝整条非法命令，存储逐条修复的行为继续保留。
- 浏览器会话检测与用户手势下权限申请仍留在现有流程中，不进入纯校验模块；后台再次检查权限，校验失败不落库。

字段 issue 不重排已有拒绝优先级：表单当前先规范化 Hydro scope，再检查会话/identifier/字段；服务先检查来源/mode/identifier/凭证，再规范化 scope。来源默认、label、domainId、URL 解码及 provider 身份键仍使用原有 helper。纯验证同步执行，不能在用户手势与 permissions.request 之间加入新的异步任务或搬到后台申请权限。

前后端现有规范化不完全一致的路径需要登记输入样例。默认保留已有边界语义，不将规则合并的副作用当作兼容迁移。

### 4.4 采集状态与覆盖规则：R01

这是主要业务改造，采用“共享规则、保留站点循环”的第一版设计。先迁移洛谷，再迁移 QOJ，每个来源分别验收。

公共覆盖构造移到 `domain/sync-coverage.ts`，让应用层不再依赖 `adapters/shared/submission-window.ts` 来创建领域结果。保留 finalizeCoverage 的冻结窗口、计数处理、非空 partial reasons 与去重语义；不新增第二份 coverage 实现。

移动领域构造时用领域叶子类型导入，避免新模块反向导入自身所在的 domain barrel。只读/冻结改动限于已有契约和常量，不能顺带深冻结 StoredData、Adapter 对象或页面草稿。

公共采集策略只接收已归一化 Submission 或稳定 ID，不接收站点 raw-record 联合类型。建议拆成下列小单元，不要求使用类：

| 策略           | 输入与职责                                                          | 必须保持的语义                                                                                                           |
| -------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 降序窗口跟踪器 | 完整页面的 submittedAt 序列与已有窗口，验证页内/跨页顺序并观察下界  | 必须有站点降序合同；无效时间或逆序后，本轮不能恢复边界信任；不能通过本地排序证明页序                                     |
| 窗口记录缓冲区 | 按原顺序加入范围内唯一记录，执行记录额度并报告 overflow             | 每个账号本轮有独立实例；窗口外不占额度；用已有 submissionKey；洛谷/QOJ 保留首次入选记录，不顺带改成 merge 或最后一条覆盖 |
| 重复页检测器   | 站点提供的完整稳定 ID 序列形成页签名                                | 相邻少量记录重复不等于整页重复；空页由站点尾部逻辑判断，不能一律判重复                                                   |
| 页进度状态     | 仅在 PaginationRuntime 真正派发逻辑页回调时递增，读取当前保留记录数 | HTTP 重试、HTML/JSON fallback 和一次认证恢复不额外计页；排队取消不计已派发页                                             |
| 失败分类       | signal、已成功页数与结构化错误，输出继续抛出或 partial 原因         | 按下述 catch 优先级迁移；无 deadline 覆盖时身份/未知错误继续抛出；首个成功页之前仍失败；只让洛谷/QOJ 使用此政策          |

调用顺序保留在站点循环中：在现有位置派发请求、验证响应与身份、完整解析和归一化、观察页签名与时间、收集记录、处理尾部证据/额度/下一页。洛谷与 QOJ 当前检查顺序存在差异，搬迁 helper 时不统一异常优先级。

下一页证据继续独立：洛谷的 count/perPage 与 count-only 路径需要保留不同可信度；QOJ 使用解析后的 hasMore；缺乏证据时记录 unverified-coverage。进度估算不是尾部证明。具体不能改写为统一的“非空页就继续”：

| 情形                                                             | 现有处理                                                                             |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 洛谷没有 count，非空页且未达到可信 since 边界                    | 立即 unverified-coverage partial，不继续猜下一页                                     |
| 洛谷仅有 count                                                   | 用整轮原始唯一 ID 数量判断是否还有页；这些 ID 包含窗口外记录，不能改成窗口缓冲区大小 |
| 洛谷空页但 hasNext 为真，或 QOJ 空页且 hasMore 为真              | unverified-coverage partial，不把空页视作已采齐                                      |
| 恰好达到 limit，但已经证明尾部或可信时间边界，且没有丢弃目标记录 | 可以 complete；不能仅看 records.length >= limit 就加 record-limit                    |
| 有目标记录因 overflow 被丢弃，即使同页证明尾部/边界              | record-limit partial                                                                 |
| 同页同时证明尾部与 since 边界                                    | 保留当前先检查尾部的 evidence 优先级，不将 exhausted 改为 window-boundary            |

页序跟踪必须观察完整的原始归一化顺序，包括窗口外、重复及超过额度的记录；过滤或本地排序之后再观察会遗漏页序证据。重复页签名保留当前 ID 序列与精确字符串语义，不把不同签名算法、大小写规范化或 across-account 缓存混入提取。

保留成功页计数的现有位置：洛谷在原始重复页检查、身份核验与归一化后递增；QOJ 在身份核验与归一化后、重复页检查前递增。成功页不等于已入选记录数；全是窗口外定位记录的成功页，之后失败仍可能返回零记录的 partial。

洛谷/QOJ 的 catch 处理顺序如下。把同组检查重新排序会改变“deadline 与身份/未知错误同时出现”时的返回值，第一轮不得重排；若希望改变这个并发边界，另写修正设计与回归用例：

1. signal 已取消且不是 `{ kind: "deadline" }`：抛原始 signal.reason，不转 partial。
2. 已有成功页且 signal 为 deadline：沿用当前 deadline partial 与诊断，先于后续错误类型检查。
3. 尚无成功页、不是 AdapterFailure、stage=identity、kind=auth_required 或 unknown：抛原始错误。
4. 其余已分类的后续失败：rate_limited 转 rate-limited，其余按当前 unavailable 规则；保留原 retryable/messageKey 与已有 partial 原因。

队列冷却是另一条必须保留的路径：application 绑定的 runPage 将派发前 RateLimitError 转为 AdapterFailure.fromTransport，再交给 Adapter；不能误判成 unknown，也不能在每一层重新包装。派发前冷却拒绝不增加 pagesFetched；首个成功页之前仍失败，有成功页后的处理按来源合同保留。原始 HTTP 429 的即时冷却登记和返回响应也不能被该转换替代。

完成结果按以下规则汇总：

1. 先处理整页，再决定停止；晚于 until 的定位页应继续，早于 since 的记录仅在边界可信时可终止。
2. 尾部或可靠时间边界允许完成，但当前页已有目标记录被额度丢弃，仍返回 record-limit partial。
3. 达到记录或页预算且无法证明覆盖完整，返回 partial；无效记录等已有原因不能被尾部证据清除。
4. partial 原因与 coverage 用一个累积入口最终构造；保留 reason/diagnostic 的现有顺序。这里只消除重复的顶层覆盖状态，页面解析器的 hasMore 和 Hydro 停止调度状态仍有实际用途，不能作为“重复字段”删除。
5. 应用层 guardCollection 与提交事务继续重检身份、范围、去重、凭证版本和代际，不能因 Adapter 已过滤就删除写入前防线。

第一版不合并五个 fetchRecent，也不将 AtCoder/Hydro 迁移到页码循环。AtCoder 的包含式升序游标、同秒停滞与详情补全，Hydro 的 ObjectId 证明、多活动共享预算与 merge 均继续使用现有实现。

Hydro 活动级 403 当前可标记 excludedByPermission，区别于账号认证失败和普通列表不可用；不能通过共享 HTTP 错误或分页失败策略把它统一改为全账号失败，反过来也不能把登录恢复失败当作无权活动排除。来源特殊规则仍留在原模块。

账号采集器不属于本轮分页去重的替换对象。保留其按 accountId 的 slot、generation、credentialRevision、since/until、boundedLimit、recheckActivities 与分页策略快照组成的共享键；now 和 UI requestId 当前不属于该键，不应无意加入使在途复用失效。900 秒计时从任务进入采集器开始，包含等待前一个任务的时间；不能移到真正执行 HTTP 时才启动。同步快照 now 与限流/队列的实时钟也不能互换。

相同任务的调用者只附加观察者，不新增可取消共享任务的独立 waiter signal；取消仍由 owner/controller 负责。保留后台注入的同一 collector、pagination、rateLimits 及默认 collector 的缓存语义，不能在新 helper 或每个消息分支中创建新实例。

只有洛谷/QOJ 迁移后仍存在明显相同的控制流程、且无需加入站点条件分支或大量回调钩子时，才另立决策提取有限页码驱动。没有这个证据，也可认定本轮 R01 已完成；复用规则不要求复用所有循环。

### 4.5 网络目标与异步生命周期：R09、R10

在 `platform/network/request-target.ts` 集中从当前 source/options 创建请求目标政策，供请求前与最终 URL 检查调用。第一版沿用 HttpRequestOptions，不新增一套对外配置 DSL。

- origin、协议、URL 凭证与端点路径按现有允许矩阵搬迁；原始 URL 与 response.url 复用同一端点判断。
- 初始凭证选项的来源一致性检查单独保留，不能被“最终 URL 合法”替代；最终响应校验不能扩大授权范围。
- 把允许和拒绝组合登记为数据驱动用例；迁移若改变任何组合，必须单列行为修正。单纯基于函数名推测更严格的目标规则不可直接落地。
- HTTP 429 仍由传输层在读取正文前登记，有限 GET 重试和响应体大小/取消清理继续由 HTTP 客户端负责。
- Timeline 的链接选择复用一个允许判断，提交/回退链接的选择顺序与原始显示方式保持不变。

请求前后共用的是目标 origin/协议/路径判定，不是把整套凭证选项检查无条件重复执行。当前浏览器层先检查原始 Cookie 选项，移除临时凭证字段和 Cookie header 后再调用物理 HTTP 客户端；新策略不能仅从清理后的 options 推断原始凭证范围，也不能让前后层各注入一次 Cookie。沿用现有校验/排队/注入/请求/恢复顺序；提前校验等时序优化另行修正。

单项和组合的 AtCoder flags、原始/最终 URL、手动/浏览器 Cookie、空 response.url 回退都纳入对照；不借去重改变 flag 交集、现有前缀匹配或重定向策略。Navigation 仍单独执行 Hydro 域限制；不能以 HTTP 允许的 origin 集合直接替代导航规则。

队列与等待放入条件实施项：确有维护收益时，将相同的串行算法提取为 `createKeyedSerialQueue`；Cookie 与 Hydro session 各创建独立实例。原有清理必须按当前 tail 判断，前一次失败不能阻塞后续任务。

分页队列仍保留自己的取消、TTL、等待与冷却状态；账号任务队列仍保留版本、代际及共享请求规则。不得将三类队列合并成通用调度器。

可取消等待函数可以共享实现，但先确定可选 signal、signal.reason 的传递与现有调用方适配规则。取消正在执行的网络回调时仍等待真实清理完成，不能用 Promise.race 提前释放锁。

固定锁顺序为 Hydro instance session → pagination → request callback → Cookie scope → physical HTTP。锁 key 仍是 origin，不能因多账号/多 domain 改为 accountId 或 scope。排队/延迟取消可以及时结束调用方等待，但内部 tail 必须保持在前一个回调之后；已派发回调只在请求与 Cookie 收尾真正结束时让后续任务通过。拒绝值为 undefined、前一次同步抛错、部分恢复失败等情形也必须保留后续队列可用性，不能新增“超时强制解锁”。

“Cookie 恢复完成”是指全部已注入字段的恢复尝试按当前顺序结束，包括报告失败的情况，不要求用永久占锁强迫恢复成功。保留 withTemporaryCookies 的局部优先级：恢复失败在全部尝试后优先抛出；恢复成功才返回请求结果或抛原请求错误，包括 undefined 拒绝值。取消 signal 不能导致跳过剩余恢复字段，不能在单次恢复失败后提前退出 finally/收尾流程。

### 4.6 HTML 与共享 UI 样式：R08、R05

HTML 实体解码放到 `adapters/shared/html.ts`。先迁移 QOJ/Hydro 的同语义版本，再迁移 branding 等差异调用；只共享明确相同的步骤。

`&nbsp;` 支持、非法 code point、重复解码顺序可能改变已有输出，应作为单独的边界修正记录。第一轮提取用旧输出做对照；QOJ 的 script/style 清理、Hydro 活动徽章移除和 AtCoder 文本提取仍由站点组合。解码不承担 HTML 消毒或 URL 允许判断。

`AnimatedSelect.css` 随组件导入，统一菜单开闭、隐藏、焦点及交互状态。先提取共同声明，再用明确的 compact/form 变体或有限 CSS 变量保留页面尺寸、动画与外观差异。避免把两套完整样式原样搬进 shared 文件后声称去重。

页面基础 reset/字体/背景与共用容器放入 `shared/styles/base.css`。Timeline 的最小宽度、横向滚动、页面布局继续在自身样式中；共享变量命名避免影响 DateTimeRangePicker、Radix 弹层和其他全局选择器。

`.select-chevron` 当前还被 DateTimeRangePicker 和同步账号弹层使用，不能直接全部挪入 `.animated-select` 的局部选择器或要求其他组件靠引入 AnimatedSelect 才获得箭头样式。提取明确的共享箭头基础样式，或保留独立组件的完整声明；三个触发器各自的 data-state/is-open 旋转和尺寸继续生效。记录 AppHeader 的 :root 设置、基础/组件/页面 CSS 的实际加载顺序与覆盖关系，迁移不能覆盖 scrollbar-gutter、页面动画或减少动画规则。

不批量替换当前只提供默认 type 的 Button/Input 包装。只有出现共同交互或视觉职责时再扩充这类基础组件。

## 5. 分阶段实施与评审单元

每个单元独立完成“迁移、删除旧维护点、验证、记录差异”。不先铺设一套无人使用的公共框架。依赖表示开始实施的前提，不要求不同单元共用一个大提交。

| 阶段/单元 | 内容与对应审计项                                     | 依赖                   | 交付与退出标准                                                                          |

## 6. 验证矩阵与可靠性门禁

测试以真实的可观察行为为目标，复用纯规则测试不替代通过 Adapter→应用→事务的回归路径。

| 类别          | 必须验证的情形                                                                                         | 通过标准                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 窗口与额度    | 两端等值、越界定位页、跨开始边界、同页重复、满额度且到尾部/边界、目标记录 overflow                     | 记录集合与原实现一致；完整性不被额度覆盖；范围外不请求详情                  |
| 页序与证据    | 页内乱序、跨页逆序、无效时间、重复整页、部分重叠、空页却仍有后续、count 缺失/count-only                | 未证明时不时间提前停止；partial 原因保留；不新增无界扫描                    |
| 失败与取消    | 第一页失败、后续 429/5xx、派发前冷却、身份/未知异常与 deadline 同时出现、排队到期、执行中取消          | 保留 catch 优先级与 RateLimitError 转换；取消不保存新结果；派发前拒绝不计页 |
| 可选补全      | 完整列表后题名/详情/品牌失败或 deadline，列表本身 partial 后补全失败                                   | 列表 coverage 与补全诊断独立；保留已完整结果与原有成功时间语义              |
| 账号与事务    | 相同请求复用、不同窗口排队、重授权、删除、清空、旧授权晚返回、提交前失效                               | 旧版本不能覆盖新版本；失效结果不入库、不误更新成功时间                      |
| 网络与权限    | 所有允许端点、错误 source/host/path、最终 URL 越界、第三方公开数据、HTTP Hydro、自定义域               | 请求与响应校验使用同一政策；授权和 Cookie 范围不扩大                        |
| Cookie 与队列 | 注入/恢复失败、部分注入、原值恢复、请求失败后续可继续、多账号同 origin                                 | 恢复完才解锁；错误优先级不变；无跨账号临时 Cookie 污染                      |
| 消息与状态    | 无 type 的失败响应、无 data 的 CLEARED、superseded/未登录、缺可选字段、错误 id、乱序进度、卸载与晚回包 | 六种成功分支及错误分支合法；既有竞态控制有效，最终事务结果优先，响应脱敏    |
| 授权输入      | UI/直接命令的非密码前后空格、纯空格密码、未知字段、CR/LF、scope 与字段同时非法、全部认证模式           | 共享基础规则且保留入口差异、拒绝顺序和 permissions.request 时序             |
| 清除与偏好    | 三种清除命令、删除账号、待授权操作、未配置/空选择、并发配置保存、清空后低 revision 回包                | 清除作用域与失效范围逐命令一致；旧回包不覆盖新草稿，不恢复空选择            |
| 配置与节奏    | 默认/自定义/恢复默认、600 秒间隔、入队后修改配置、worker 重启的 session 冷却恢复                       | 既有单位/上限/冻结保持；计时含排队，手动同步不绕过冷却                      |
| UI            | 下拉、日期和同步弹层箭头、键盘/隐藏焦点、CSS 顺序、窄屏滚动、页面切换、减少动画                        | 三类触发器与两页均完成验收，不只检查 AnimatedSelect                         |
| 扩展接入      | 暂时加入一个测试用来源定义或漏掉现有映射                                                               | 类型/依赖/manifest 检查能发现缺失项；页面无采集实现依赖                     |

采集迁移期间，用固定 fixture 记录改造前的输出和请求轨迹，再用同一输入对照新实现。对照应包含记录顺序/字段、coverage、diagnostics、错误字段与逻辑页数量；冻结时间与随机值，归一化随机 requestId 时仍验证其引用关联，不能忽略 accountId/providerAccountKey、原因顺序或进度先后。不要在生产中同时跑两套采集，也不长期保留旧实现作为测试 oracle；对照完成后留下独立期望与回归用例。

验证按变更范围执行：

- 每单元：typecheck、lint、相关测试、格式与 diff 检查。
- S1-B 起：执行新增的 `pnpm audit:architecture`；该命令现已实现，使用已安装 TypeScript 7 的原生 AST/解析器；缺失命令或解析失败不能作为通过。
- 改采集/消息/授权/网络：执行完整 `pnpm test`，按需要补 `pnpm test:contract`；没有新失败或后续修改时不重复整轮测试。
- 改来源依赖/权限/构建：执行 build 与 audit:manifest，检查页面静态依赖，并比较相同环境下的产物尺寸；不以源码可达性直接推断 bundle 大小。
- 改共享 CSS：执行受影响 UI 测试及 Chrome/Edge 视觉/交互验收；jsdom 通过不代表视觉完成。
- 最终交付：执行全部现有门禁，另显式检查本计划及相关 Markdown，因为当前 `format:check` 脚本不覆盖 docs。

```bash
pnpm typecheck
pnpm lint
pnpm test
pnpm test:contract
pnpm format:check
pnpm exec prettier --check docs/plan/code-reuse-upgrade-plan.md
pnpm build
pnpm audit:manifest
pnpm audit:architecture
git diff --check
```

真实站点验收使用人工授权的浏览器会话或既有可选 live 测试；不能把未运行的 live/视觉检查标记为通过。在浏览器矩阵中记录日期、平台、场景与实际结果，按涉及的功能决定完成范围。

## 7. 新增 OJ 的固定接入步骤

完成升级后，新增来源按以下顺序操作：

1. 调研并记录身份入口、认证模式、来源范围、列表分页/排序依据、预算、错误与可选详情。没有排序证据就保守处理覆盖。
2. 更新 SOURCE_IDS，填写 sourceDefinitions、分页默认政策、UI 图标及 manifest 必要的可选权限；穷尽检查发现遗漏。
3. 在独立 Adapter 目录实现 authorize、fetchRecent 和必要的会话/品牌方法，注册到后台实现表。只使用注入的 HttpClient、PaginationRuntime 和共享领域规则。
4. 按来源能力选择既有小策略。无法匹配的游标或活动模型保留站点实现，不能为了接入而给公共策略堆 source 分支或空回调。
5. 编写站点解析/身份 fixture 与 Adapter→应用的覆盖用例；补权限允许/拒绝矩阵和浏览器验收。初始未知来源行为应明确报告 partial 或 unsupported。
6. 更新支持来源、隐私/权限说明、研究证据与验收记录。来源出现相同需求后，再判断是否值得提取新的公共能力。

通用 UI 不新增来源 switch；站点确有特殊用户输入或展示需要时，用明确的元数据或小组件扩展，不把网络诊断内部细节直接堆入产品流程。

本计划不新增一套无人消费的 capabilities 布尔矩阵。使用已有 OJAdapter 端口和可选方法；只有真实用例需要新能力时，才演进相应合同。

## 8. 回退方式、状态记录与完成标准

每个评审单元保留独立提交。核心路径保持单实现，临时 re-export/旧查询入口限定到当前迁移阶段，全部调用迁移后移除。回退按依赖逆序，先恢复依赖新接口的消费者，再撤销提供者，重新执行相关检查；不要一并撤销仍被其他已验收单元使用的上游公共模块，更不能回退其他任务的提交或未提交修改。schema 不变的回退不需要迁移或清空用户存储。

回退构建、重新加载扩展或重启 worker 前，先让已派发同步、HTTP 和 Cookie 收尾完成；当前内存锁并不提供跨 service worker 的互斥/恢复保证。session 冷却的重启恢复继续按已有合同验收，不将它误称为任务或 Cookie 锁恢复。旧页面与新后台在合法 schema 2 消息上的兼容也要验证；变更源码不能假定所有已打开页面已经加载新 bundle。

如果某个单元必须改变持久化结构、消息 schema、权限集合或业务合同，应停止将它视为本计划内的等价迁移，单独设计兼容、数据升级与回退方案。本计划本身不授权用清空缓存解决迁移问题。

每阶段记录：基线版本、修改入口、已删除的旧维护点、行为差异、相关测试与浏览器结果、依赖图/构建尺寸变化，以及尚未完成的条目。使用已有 QA/发布检查文档，避免新增另一套彼此矛盾的完成状态。

核心交付验收清单：

- [x] R02：来源名称、首页与固定 origin 有权威定义，UI/权限不依赖完整采集注册表。
- [x] R03：页面统一消息客户端，后台公共响应封装统一；无调用者指定任意响应类型的断言封装。

- [x] R01：洛谷/QOJ 共用采集状态与规则，coverage 构造归领域，站点证据与应用写入防线保留。
